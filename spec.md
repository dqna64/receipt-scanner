# The Project: A personal receipt scanning web app

This project is a receipt scanning app for personal use.

# Project ground rules

We will design it to suit my own requirements as the (currently only) user, while building it as a genuine multi-tenant SaaS: every signup is a first-class, equal peer — no privileged "owner" account, no first-user special-casing. All per-user data (receipts, items, categories, tags, payment methods, recurring defs, sessions) is scoped by user_id with fully isolated access and no cross-account interactions. "Scalability best practices without the cost of scaling" refers to INFRASTRUCTURE (one box, no horizontal scaling, no Redis/queue) — NOT to the tenancy model, which is real multi-user from day one. Being the only user today is incidental; nothing in the design assumes it.

# Features & User Stories (M1)

Currently one user ("I"), but every story is written for a multi-tenant SaaS — any signup gets the same isolated experience. Stories marked (open) depend on decisions still being discussed.

## Auth & accounts
- Anyone can register an account (email + password), self-service, the way any SaaS works — all signups are equal peers, no first-user privilege, each gets its own fully isolated tenant. Open registration is guarded by ordinary SaaS abuse controls, NOT a bootstrap token: rate limiting (decided) + email verification (decided as REQUIRED before public open signup — see Auth in Architecture; gates spam accounts and, critically, LLM-cost abuse since each account can spend scan money). Registration seeds that new user's own default categories + "cash" payment method (per-user, at signup — see Auth).
- I can log in and stay logged in on my phone and laptop (session cookie, ~30-day sliding expiry) and log out. Self-service password reset (decided, needs email — same infra as verification).
- Login endpoint is rate-limited; the registration endpoint is rate-limited too (open signup on a public host — throttles automated account/cost abuse). Rate limiting is BOTH per-IP AND per-account (decided 3b) — per-IP alone is porous behind CGNAT/mobile carrier NAT/shared networks, per-account alone doesn't stop a credential-stuffing sweep across many emails from one source; both apply together.
- Password reset invalidates ALL of that account's existing sessions (decided 2c) — a reset implies the account may have been compromised, so leaving old sessions alive would defeat the point.

## Capture
- I can upload one or more receipt photos from my phone camera or a file picker. Client re-encodes/downscales before upload (handles HEIC, cuts vision-token cost).
- Multi-image receipts (decided, no toggle needed): a receipt entry can own MULTIPLE images, not just one — overlapping shots of the same receipt, the same receipt in different lighting, a correction/re-issued invoice screenshot, or a receipt + a separate invoice for the same purchase, are all images that belong to ONE transaction. There's no special "grouped vs separate" mode to choose: an upload action IS "these N images are one receipt" — 0-or-more images per receipt is just the primitive, no toggle required. Photographing several DISTINCT receipts in one session is simply several upload actions, one per receipt (a client-side convenience can loop one-image-per-receipt over a camera-roll multi-select for that common case, but that's a UI shortcut over the same primitive, not a data-model branch). I can also add more photos to an existing receipt later (reviewed or not) via an "add photo" action — the generalized form of the existing attach-with-verify-scan flow (see Recurring), now for N images instead of exactly one. The scanner reconciles ALL of a receipt's images together in a SINGLE extraction call — resolving overlap and conflicts across images (e.g. a correction email superseding a figure on the original photo) into one set of fields/items, not one result per image (see Scan pipeline). A per-receipt image count cap (config, default 8) bounds LLM vision cost — every verify-rescan resends the receipt's FULL current image set, so total images on a receipt is what drives cost, not storage (see Architecture). The cap is enforced when a NEW image is being ADDED (upload or add-photo rejects past the cap); merge is EXEMPT (consolidating existing legitimate images doesn't add new content or increase aggregate scan cost — two 5-image receipts merging into one 10-image receipt costs about the same to rescan as the two separately would have). The exact-duplicate hash check runs per IMAGE, not per receipt — scoped (user_id, image_sha256) across every image the user owns, whichever receipt it's attached to.
- Currency (decided): the scanner extracts a best-guess currency per receipt (symbol/text on the document) in addition to doc-type; total_cents/direction; defaults to AUD only when the document gives no signal. Editable at review like any other field — a wrong currency previously would have silently misfiled a foreign receipt into the AUD bucket forever (currencies are never combined natively — see Insights), so getting this right at scan time matters more than most fields.
- Each image immediately creates or updates a receipt row (scan_state=uploaded) — nothing is ever lost in a waiting state. I see it appear in history with a live status trace: uploaded → scanning → pending review (or scan failed). (That user-facing trace is the scan_state lane plus the derived needs_review state; see Invariants.)
- On scan failure I can retry the scan or fall back to entering the fields manually against the stored image.
- I can record a cash/no-receipt transaction via a manual entry form (merchant, date, total, currency, payment method defaulting to cash, category, tax-deductible, note, optional items). Manual entries are born with reviewed_at set (proposed_at NULL) so they count immediately — I typed them, no review needed.
- Quick-add (required by the <15s friction ceiling): the manual form defaults everything defaultable (date=today, currency=AUD, payment=cash) so a coffee is amount + merchant + category and done; recently-used merchants autocomplete.
- I can record a refund/return: scan the return docket (they're receipts) or manual entry; kind=refund (inflow), optional link to the original receipt.
- I can record a reimbursement I receive (PayID/Beem etc.): a manual entry, kind=reimbursement (inflow). These usually arrive with no purchase context — I annotate which expense they offset (same category as the original so category charts net correctly; optional link).
- I can record an ATM withdrawal as a transfer — visible for cash reconciliation, never counted as spend (the individual cash purchases are the spend).
- I can record INCOME (decided in M1): scan a paycheck/payslip (kind-aware scan classifies it as income and extracts employer + pay date + NET amount — see Scan pipeline), or enter income manually (salary, casual/gig pay, bank interest, distributions/dividends, a friend gifting me money). Income is kind=income (inflow), carries an income category (salary/interest/dividends/other-income — the category picker filters to income categories when kind=income), does NOT count as spend, and feeds income stats + the credit side of reconciliation. Manual income is born reviewed (counts immediately); a scanned paycheck goes through review like any scan. Recurring income (fortnightly salary, monthly interest) is supported via a recurring definition with kind=income (see Recurring).

## Transaction kinds & stats rules (decided)
- receipts.kind: purchase (default) | refund | reimbursement | income | transfer. `income` is now IN M1 (decided 2026-07-18 — salary/paychecks, casual income, bank interest, distributions/dividends; scanned from payslips or manually entered). The enum stays extensible.
- Magnitude + direction money model (decided 2026-07-18 — replaces the old signed-amount convention): `total_cents` (and item `amount_cents`) are stored as a NON-NEGATIVE MAGNITUDE (≥ 0), never signed. Physical cash direction is carried EXPLICITLY in a `direction` field [inflow | outflow] (= bank credit vs debit), NOT as the sign of the amount. Stats apply per-kind signs in the query/view, not in storage. Rationale: income made "negative = money in" unintuitive, and transfers can go EITHER direction (ATM withdrawal = outflow, share-sale proceeds = inflow) so direction can't be derived from kind alone. `direction` is the reconciliation key (which bank-statement side a row lands on); `kind` is the semantic role. For the fixed kinds a CHECK enforces the canonical direction (purchase → outflow; refund/reimbursement/income → inflow); transfer sets direction freely. ("transfer" is a KIND, not a direction value — a transfer still has an inflow/outflow direction; keeping direction a clean two-value field avoids a redundant tri-state.)
- Kind → stats role:
    - purchase: outflow, +spend.
    - refund: inflow, −spend (nets against spend, same category — e.g. return docket, cashback/reward credit categorized "rewards").
    - reimbursement: inflow, −spend (nets against the specific expense it offsets; annotate which — same category as the original; optional link). A Beem/PayID repayment for something you fronted is a reimbursement.
    - income: inflow, does NOT touch spend — it's a separate axis, summed into INCOME stats, and feeds the CREDIT side of reconciliation. (A friend GIFTING you money with no expense to offset is income, not reimbursement.)
    - transfer: own-money movement, excluded from BOTH spend and income. Covers ATM withdrawals, credit-card bill payments (the card's purchases were already counted), moves to savings/investments (incl. after-tax personal super contributions — see super boundary), loan/BNPL principal repayments (the interest/fee portion is a real purchase, category "fees"), and the RETURN direction too (selling shares, withdrawing from savings = inflow transfer).
- Spend stats = Σ(magnitude with per-kind sign) over kinds {purchase (+), refund (−), reimbursement (−)} ONLY — NOT "≠ transfer" (that would now wrongly include income) — further excluding purchases paid with stored-value methods. Income stats = Σ(income magnitude). Transfers in neither. (The per-kind sign lives in the stats VIEW, single-sourced — see schema.)
- Expenses incurred for others still count in full as my expense; incoming reimbursements offset them as inflow reimbursement entries.
- Refundable deposits/bonds (rental bond, hire deposits): purchase (category "bonds/deposits") + linked refund when returned. If the bond is docked, the books are already correct.
- Stored-value convention: gift card/Opal/prepaid TOP-UPS count as the expense at top-up time (kind=purchase, categorized e.g. "transport", "gifts"). Purchases PAID WITH a stored-value method are recorded (receipt, items, history, dedupe) but excluded from spend stats — the money was already counted. Requires payment methods to carry a stored_value flag.
- Cash is the opposite: ATM withdrawal (kind=transfer, outflow) excluded; each cash purchase counts at spend time.
- The stored-value convention is chosen PER payment method via the stored_value flag: flag an Opal/gift card (spend books at top-up), leave a travel money card (Wise) unflagged and record its loads as transfers to keep per-purchase categories abroad.
- Super boundary (decided 2026-07-18): record ONLY what touches my bank account. Net pay = income (inflow); after-tax personal super contributions = transfer (outflow to a retirement asset). Employer SG and salary-sacrifice super never hit my bank (employer → fund, or deducted pre-tax from gross) and are OUT OF SCOPE — this app reconciles against my bank account, so gross-salary → PAYG-tax → super → net decomposition is payroll accounting, not spend/income tracking. Paycheck scanning therefore records the NET pay as the income amount (the payslip's gross/tax/super lines may be captured as informational best-effort items but never feed stats or reconciliation).
- Investments record the CASH MOVEMENT only, not the asset (decided 2026-07-18): buying shares/ETFs = transfer (outflow); selling = transfer (inflow); brokerage fee = a separate purchase, category "fees". Units held, cost basis, and market valuation are NOT represented — portfolio/holdings tracking is a different domain and explicitly out of scope. Dividends/distributions received in cash = income; a DRP (reinvested distribution) = income (inflow) immediately followed by a transfer (outflow) if you want both legs, or just skip the wash if you only track cash.
- Bank interest: interest the bank PAYS me on savings = income (inflow, income category "interest"); interest CHARGED to me (loan/credit-card) = purchase, category "fees" (outflow). Direction disambiguates the two.
- Small conventions: pre-auth holds ($1 petrol, hotel holds) are not transactions — reconcile settled lines only; cashback/reward credits = refund (inflow) with category "rewards" (or ignore); bank/account fees, fines, ATO payments = ordinary manual purchases; zero-total receipts (warranty swaps) are allowed.

## Review
- I have a "pending review" queue (oldest first, with a count badge) of everything machine-generated: scanned receipts and auto-created recurring charges.
- The review screen shows the receipt's image(s) alongside the extracted fields; I can correct merchant, date, total, currency, payment method, tax-deductible, note, and line items (incl. each item's category — categorization is item-level, see below), then mark reviewed.
- Line items are extracted and auto-categorized by the scanner but OPTIONAL to review (decided): marking reviewed only requires confirming receipt-level fields — a 40-item grocery shop is not a chore. Item-level data is best-effort: as good as the auto-labels plus whatever I choose to correct.
- If line items don't sum to the total, I get a warning, not a block (discounts/rounding are real).
- Categorization (decided, revised 2b): categorization is ITEM-LEVEL ONLY. Receipt-level fields stay limited to properties of the transaction itself — merchant, date, payment method, tax-deductible, note; `receipts.category_id` is REMOVED. One user-editable category taxonomy (seeded with sensible defaults). Every receipt that should count toward category-based stats has ≥1 item: for a scanned receipt these are the extracted line items (already the case — items are auto-created by the scanner); for manual/quick-add entry, the single "category" field the fast-entry form shows is UI SUGAR — it writes ONE implicit item under the hood (name=merchant, amount_cents=total_cents, category=picked). The <15s quick-add flow is unchanged for the user; category breakdown becomes accurate and consistent for both single-line and itemized receipts. (This fixes a real ambiguity: a receipt-level category could silently disagree with item-level categories on a mixed-basket receipt — e.g. a Costco trip categorized "groceries" at receipt level despite $200 of $300 being electronics at item level. Only item-level breakdown is correct by construction now.) Items stay OPTIONAL TO REVIEW (a 40-item grocery shop is still not a chore) but are not optional to EXIST for stats purposes: a receipt with zero items shows as "uncategorized" in breakdowns — the honest state, not a data gap. Each item carries at MOST ONE category. The scanner's structured-output JSON schema embeds the current taxonomy as an enum at item level, so the LLM assigns categories from MY list at scan time; review corrects. New category = edit the list; next scans pick it up automatically. Categories are live-joined: renaming keeps the stable id (propagates to all history), re-categorizing an old row is reflected on the next fetch of any historical analysis, and deleting a category is ON DELETE SET NULL (the item becomes uncategorized, live) — not blocked, not snapshotted.
- Income items (decided): a payslip's items work the same way — one item carries the NET PAY amount + income category (this is the item category breakdown's source for income too). Gross/tax/super lines (best-effort, super boundary) are marked `informational=true` and excluded from every amount-sum, category-breakdown aggregation, and the sum-mismatch warning (which doesn't apply to them by design — they were never expected to reconcile against net pay).
- Tags (decided): a SECOND user-editable taxonomy, ITEM-LEVEL ONLY, MANY-per-item (0..N) — cross-cutting labels orthogonal to the single category (an item categorized "groceries" can be tagged "japan-trip" + "work-reimbursable"). Like categories, the current tag list is embedded as an enum in the scanner's per-item output schema, so the LLM PROPOSES tags at scan time; tags are best-effort (item-level, no accuracy gate) and reviewer-correctable. New tag = edit the list; next scans pick it up. Deleting a tag removes its associations (ON DELETE CASCADE on the join, live); renaming keeps them (stable id).
- Dedupe (decided flow): dedupe is not a separate flow — it's a match panel inside the new receipt's review screen, the screen every scanned receipt already passes through. ONE tolerance-band matching rule surfaces candidates (decided — an earlier "exact total for has-image, band for imageless" split was rejected on re-review: it created an OCR-variance blind spot where two photos of one receipt whose scans differ by a cent, and whose hashes also differ, would never surface as a possible duplicate). The panel is advisory (nothing auto-executes), so surfacing should ERR TOWARD showing a candidate; the has-image vs imageless FLAVOR governs only the offered ACTION, not the match tightness.
    - Match rule (all candidates): same currency; total within the TOLERANCE BAND abs(total − candidate.total) ≤ max(match_total_abs_cents, round(match_total_pct × candidate.total)) (config defaults match_total_abs_cents=200 / $2.00 and match_total_pct=0.05 / 5%); purchase_date within ± the dedupe day window; fuzzy merchant via a `MerchantMatcher` interface (decided 3a — `similarity(a, b) -> score`), first implementation Postgres `pg_trgm` similarity(), swappable later for a different algorithm or an LLM-judged similarity call without touching the dedupe query shape (same provider-swap pattern as ScanProvider/SearchProvider). Candidates are ALL matches ranked by match strength (monotonic in closeness — an exact-total same-day same-merchant hit ranks top), in two labeled flavors:
    - WITH image(s) = "possible duplicate" (all images from both receipts side by side; actions: discard this upload / keep both). The band (not exact-only) means an OCR-variance re-photo of one receipt still surfaces; a rare false pair (two similar coffees) just shows an extra suggestion the user dismisses with keep-both — cheap, since nothing auto-executes.
    - imageless (pending/confirmed recurring, reviewed manual entries) = "matching transaction" (actions: merge into it / keep both). The band is what lets a variable utility bill (recurring pending row created at expected_amount_cents, real invoice differs) or an approximately-typed manual entry still match — the whole point of "upload the real invoice for a pending recurring charge, dedupe offers the merge".
    - NOTHING executes without an explicit click — the suggested action is only visually highlighted. Merge uses verify-scan semantics (fill empty fields only, never overwrite; the upload's existing scan is reused, no re-scan), mismatches resolved inline in the panel. Merge mechanics (decided, updated for multi-image): ALL of the source's images (its receipt_images rows) move to the target — appended to the target's image set, not overwriting it — plus raw_ocr_json moves to the target; scanned items copy over only if the target has none, any inbound references to the source (offsets_receipt_id, recurring_id, purchase_receipt_id on other rows) are repointed source→target, then the source row is deleted (the image objects are retained — ownership transfers). Discarding a duplicate deletes both the row and all of its stored image objects. The upload page's live status trace shows "⚠ possible match found" when the scan lands, deep-linking to review — near-immediate feedback without blocking upload (field matching physically can't run at upload time; it needs scan output).
- Exact-duplicate upload check (decided, updated for multi-image): each image (a receipt_images row) stores image_sha256 (of the normalized image; plain index scoped (user_id, image_sha256), not unique). Upload/attach computes it after normalization and, on a hash hit against ANY image the user owns (whichever receipt it's on), returns a conflict identifying the existing receipt + image ("are you sure? [shows existing]") WITHOUT storing the new image; client re-submits with force=true to proceed. The only dedupe check that can run at upload time; also saves a wasted scan per double-tap. Cross-libvips-version hash drift just degrades to the field-match backstop.
- Search (decided 1c): a simple search box over Browse — merchant, store_name_raw, note, and item names (ILIKE, scoped to the user). Implemented behind a `SearchProvider` interface (`search(user_id, query, filters) -> ranked receipt ids`) so the frontend/API contract (`GET /search?q=`) stays stable if the backend is later swapped for a real full-text/trigram index, Elasticsearch, or an LLM-based query interpreter — same swap-invisibility pattern as `ScanProvider`. M1 ships the ILIKE implementation only.
- I can re-open and edit a reviewed receipt later without it losing reviewed status, and delete any receipt (with confirmation).

## Recurring
- I can create/edit/pause/delete recurring transaction definitions: name, merchant, expected amount + currency, cadence = custom interval (decided: every N days/weeks/months/years, anchored to a start date — covers weekly through annual and odd billing cycles; calendar arithmetic with month-end clamping, see Recurring interval semantics), default payment method/category/tax-deductible.
- Recurring definitions can be finite (decided): optional end_date or occurrences_total (a fixed target count, not a decrementing counter — see schema); auto-deactivates when exhausted. Installment plans (Afterpay/Zip: 4 fortnightly payments) are finite recurrings with occurrences_total=4 and an optional link to the originating purchase receipt.
- Recurring definitions carry a kind [purchase|transfer|income] (decided; income added 2026-07-18): auto-savings and credit-card autopay are recurring transfers; salary/paychecks and monthly bank interest are recurring INCOME (inflow). Generated rows inherit the kind + direction — transfers/income stay out of spend stats; income feeds income stats. The generation engine (idempotent ordinal, catch-up, finite ends) is kind-agnostic, so inflows flow through unchanged: a recurring salary auto-creates a pending income row on payday that I confirm (= review), same as any recurring charge.
- Dedupe matching against a recurring pending row is tolerant on BOTH date (± a few days, billing date drifts) AND total (the tolerance band above — the actual charge differs from the expected amount, esp. variable utilities). This is why imageless candidates never use exact-total matching (see Dedupe).
- On the expected date a pending receipt is auto-created. Confirming = reviewing it (adjusting the actual amount if it differs); if the charge didn't happen I delete the pending receipt; if I cancelled the subscription I pause/delete the definition.
- If I upload the real invoice for a charge that already has a pending recurring receipt, dedupe offers the merge.
- Direct attach with verify-scan (decided, generalized for multi-image): from ANY receipt — imageless (source=manual or recurring) OR already carrying images — I can add one or more images: POST /receipts/:id/images, same normalize→store pipeline as upload, each new image becomes a receipt_images row and sets scan_state=uploaded; the exact-dup hash check runs per image here too, mirroring upload semantics (decided): on a hash hit the add is rejected with a conflict {duplicate_of: {receipt_id, image_id}} before anything is stored; the client dialog offers (a) re-submit force=true to add it anyway (stores an independent second copy under its own image_key — the sha index is non-unique precisely to permit this) or (b) merge instead — deep-link to the existing receipt's review screen with the match panel open and this receipt force-included as a pinned candidate (?suggest= on the matches endpoint; field matching alone might not rank it if the entered fields are off). The merge is the standard merge-from with the imageless (or fewer-signal) receipt as TARGET (its user-entered fields are the trusted ones) and the other as SOURCE (donates its images/ocr/items, then deleted — also un-double-counts stats if both were reviewed). The existing worker (re-)scans the receipt's FULL current image set (kind-aware, using the row's known kind) — a verify-rescan always resends every image the receipt owns, not just the newly added one, so the LLM has complete context; cost scales with image count, which is why the per-receipt image cap exists. Worker mode discriminator (decided): mode is chosen by TRUST, not provenance — reviewed_at IS NULL → extraction mode (scan writes structured fields); reviewed_at IS NOT NULL → verify mode (fill-empty-only + compare, below). (`source` no longer gates this: a source=scanned row that scan-failed and was then manually filled has reviewed_at set, so a retry VERIFIES rather than clobbering the typed values — see Invariants, trust-gated scan mode.) Scan is verification, not extraction: it NEVER overwrites user-entered values — it fills only empty fields (items, store_name_raw, raw_ocr_json), then compares scanned vs recorded fields (total exact; date ± dedupe tolerance; merchant fuzzy). Review/stats state is DERIVED from timestamps, not a status column (see Invariants): a completed scan stamps proposed_at, and needs_review / counts_in_stats fall out of proposed_at vs reviewed_at. All match → the scan re-stamps reviewed_at (≥ proposed_at) so the row stays reviewed silently, no queue trip; any mismatch → proposed_at now leads → the row is needs_review with the diff shown at review. A never-reviewed row prefills and becomes needs_review as normal. Terminal scan failure touches NEITHER timestamp: a previously-reviewed row stays reviewed (attach degrades to evidence-only) — a confirmed transaction can never land in scan_failed over an attach glitch. Because proposed_at is stamped only when a scan COMPLETES, a reviewed receipt never leaves stats during an in-flight re-scan — even across a process crash and the full reclaim window (the old "brief stats blip" is designed out). Upload-first dedupe→merge remains available.

## Notifications (decided 1d — abstraction, Discord first)
- The app can nudge me so the habit-formation goal (pending queue hits zero weekly, capture within 3 days — see Success Criteria) doesn't rely purely on me remembering to open it. Behind a `Notifier` interface (`notify(user_id, event, payload)`), swappable per-backend (Discord webhook, email, later push) the same way `ScanProvider` is swappable per-LLM-provider.
- M1 ships ONE concrete backend: a per-user Discord webhook URL (simplest to stand up, no email/SMTP infrastructure — deliberately DECOUPLES this feature from the still-open email-infra decision, which is about verification/reset only, a separate concern).
- M1 triggers: (a) a weekly digest if the pending-review queue is non-empty (a scheduled job, same shape as the recurring-generation timer), (b) a receipt hitting terminal `scan_failed` after exhausting retries. Config-gated / no-op if no webhook is configured, so a fresh clone still runs with zero setup.

## Browse
- "Upload history": all transactions, chronological, filterable by kind (purchase/refund/reimbursement/income/transfer), direction (inflow/outflow), state (scan_state and/or the derived needs_review/reviewed), date range, merchant, item category, item tag, payment method, tax-deductible, source (scanned/manual/recurring). (Filtering by "receipt category" is gone — categorization is item-level only, see Review.)
- Free-text search (decided 1c): a search box across merchant/store_name_raw/note/item-name, scoped to my own data, composable with the filters above. M1 implementation is Postgres ILIKE behind a swappable `SearchProvider` interface (see Architecture) — the search box itself doesn't know or care which engine is behind it.
- Receipt detail view with zoomable image (image**s** — see multi-image Capture).

## Insights (all decided; confirmed rows only (is_confirmed) — see Invariants; never summed across currencies natively). SPEND insights select through v_countable_spend (spend-kind allowlist + no stored-value-paid purchases); INCOME insights through v_income; CATEGORY-based insights select through the item-level counterpart views (v_countable_spend_items / v_income_items — see schema); the RECONCILIATION insights read the base v_receipt_state and slice by `direction` — see the view layering in the schema.
- Monthly spend trend: total reviewed spend per month (receipt-level total, category-agnostic — via v_countable_spend).
- Category breakdown: spend by category for a selected month/range — ITEM-LEVEL (decided 2a, see Review categorization), via v_countable_spend_items; a receipt with no items shows as "uncategorized". This subsumes the old separate "item-category filtered trend" — there is now one category-breakdown mechanism, not two that could disagree.
- Filtered spend trend: the monthly trend narrowed by dimension selections — merchant and/or item category (e.g. "junk food over time"). Item-category trends aggregate item amounts (excluding informational items), not receipt totals, and are best-effort (auto-labeled).
- Income trend + income-by-category (decided M1): total income per month (via v_income, receipt-level) and a breakdown by income category (salary / interest / dividends / other-income) — item-level via v_income_items (the payslip's net-pay item), excluding informational gross/tax/super lines. Separate axis from spend, never netted into it.
- Net cashflow (decided M1, falls out for free): income − spend per month (the two trends overlaid), so I can see whether I'm net saving. Transfers excluded from both sides.
- Tax-deductible running total for the current Australian FY (Jul 1 – Jun 30, decided), with its receipt list. All "this year" filters use AU FY. (Income is recorded but M1 makes no attempt at income-tax/PAYG reckoning — that's payroll accounting, out of scope; the tax view stays the deductible-expense list.)
- Payment-method crosscheck: monthly totals per payment method to reconcile against bank statements — NOW TWO-SIDED (decided M1, income in scope): debits (outflows) AND credits (inflows: income, refunds, reimbursements, inbound transfers), matched by `direction`. The M1 reconciliation goal is a full balance on BOTH sides, not debit-only.
- Cash view: cash withdrawn (transfers) vs cash spent per month — the reconciliation story for statement ATM lines.
- SPEND stats follow the spend rules via v_countable_spend / v_countable_spend_items (signed amounts, stored-value exclusion); INCOME stats via v_income / v_income_items; reconciliation slices the base view by direction (that's its job — see view layering).
- FX note: foreign-currency receipts never exactly match the AUD card charge (rate + fee); reconciliation for those is approximate by design. Native per-currency views (all of the above) stay exact and never combine currencies.
- Combined (AUD-equivalent) view (decided 4a, opt-in and explicitly approximate): I can manually enter an exchange rate on any non-AUD receipt (`fx_rate_to_aud`, e.g. the rate at the exchange booth/ATM I actually used) — the app stores a computed `aud_equivalent_cents` at entry/edit time (a rate is a point-in-time user decision, not live-recomputed from a market feed). A separate, additive "combined" insight sums native AUD amounts plus `aud_equivalent_cents` for rows where it's set; rows without a rate are simply excluded from this one view (still fully visible in their native per-currency views, unaffected). This does NOT change the "never sum across currencies" invariant for the native views — it's one clearly-labeled opt-in extra.
- CSV export of receipts + items for a date range, for tax time.

## Out of scope for M1
- split payments
- team/household SHARED accounts (multiple users seeing the SAME data): tenancy is one-user-per-account with full isolation; multi-user here means many independent tenants, not shared workspaces. Invites, roles, and shared receipts are post-M1.
- billing/subscription/plan limits: open signup is free; per-user cost quotas are a follow-on (see the abuse note in Auth).

# Architecture & Stack (decided)

- Backend: C++ (chosen deliberately as a learning vehicle for the language; not the "natural" fit for a CRUD-heavy app, but acceptable given low scale/low risk)
    - Architecture: single all-async Drogon process, coroutines throughout (decided — maximizes C++ async learning; no separate worker binary)
    - Framework: Drogon (batteries-included: routing, JSON, async/coroutines, ORM-lite) to avoid hand-building HTTP plumbing
    - DB access: Drogon's async DbClient with coroutines (`co_await execSqlCoro`). libpqxx rejected: blocking, would stall the event loop
    - JSON: nlohmann/json
    - Outbound HTTP (to scan provider): Drogon's async HttpClient (`sendRequestCoro`). cpr/Boost.Beast rejected: blocking / too low-level
    - Known tradeoffs to budget for: async orchestration of the scan pipeline (upload -> background job -> status transitions) is more manual than in Python/Node; less JSON/schema-validation/ORM convenience; slower iteration (compile times, verbose error handling); no native LLM/OCR SDKs so provider calls are hand-rolled REST+JSON.
- Money: integer cents end-to-end (decided) — BIGINT in Postgres, int64 in C++, plain integers in JSON. Avoids float drift through nlohmann/json doubles; makes dedupe total-matching exact. Frontend formats for display. Amounts are stored as a NON-NEGATIVE MAGNITUDE (≥ 0); cashflow direction is the separate `direction` field, not a sign on the amount (decided 2026-07-18 — see Transaction kinds). Sub-cent upgrade path (if ever needed for unit prices like fuel $1.859/L or a future finer-grained domain): RESCALE the integer unit (e.g. store micro-dollars, 1e-6, in the same int64) — never switch to floats or NUMERIC. Keeps exact arithmetic + exact-match dedupe. Whole receipt totals/line amounts are always whole cents (that's what you're charged), so this stays a documented escape hatch, not an M1 change.
- Database: Postgres
- Object storage (decided): self-hosted MinIO (S3-compatible), running in Docker Compose on the private network, never publicly exposed
    - Access from C++: hand-rolled SigV4 client over Drogon's async HttpClient (PutObject/GetObject/DeleteObject only; ~150 lines of OpenSSL HMAC). AWS SDK rejected: huge build tax, own thread model, 99% unused. minio-cpp rejected: blocking.
    - Cloud-portability requirement (decided): the S3 client takes endpoint, region, credentials, and addressing style (path-style for MinIO, virtual-hosted for AWS) from config — swapping MinIO for AWS S3/R2/B2 later is a config change plus `rclone sync`/`mc mirror` of the objects. ImageStore interface above it keeps even non-S3 backends possible.
    - Multi-image receipts (decided 1a): a receipt owns a SET of images (`receipt_images`, not a single `image_key` column on receipts — see schema), each independently normalized/stored/hashed exactly as before. Image serving becomes `GET /images/:id` (proxy, auth-checked via the owning receipt's user_id) rather than one per-receipt image endpoint. A config cap (default 8, NOT a storage constraint — receipt_images makes storage cost linear and cheap regardless) bounds total images per receipt because every verify-rescan resends the FULL set to the LLM, so uncapped images = uncapped-and-repeated vision-token cost, and (on an open-signup multi-tenant host) a real abuse surface. Enforced at add-time (upload / add-photo rejects the (N+1)th image on a receipt already at the cap); merge is explicitly EXEMPT — it recombines images that already existed and already cost what they cost, so a post-merge receipt can legitimately exceed the cap.
    - Image normalization (decided): server-side canonical version regardless of what the client uploads — decode → apply EXIF orientation → STRIP all EXIF (phone photos embed GPS) → downscale to 2048px long edge → encode WebP q80 (~150-350KB/receipt, ~0.5GB/yr; crisp above Haiku's 1568px vision cap, headroom for future models). Original discarded. Library: libvips.
    - CPU-bound rule: normalization runs on a small worker thread pool, resuming the coroutine after — never on a Drogon IO loop.
    - Serving (decided): backend proxy — GET /receipts/:id/image streams from MinIO through Drogon, guarded by the session cookie. Presigned URLs rejected for now: would force MinIO onto the public internet and re-tie the frontend to whichever storage host is in use, breaking swap-invisibility.
    - Images are immutable after normalization → proxy responds with `Cache-Control: private, max-age=31536000, immutable`; the browser cache is the only cache that matters at one user.
    - CDN note / upgrade path: proxying does forgo CDN caching of a future cloud bucket — irrelevant here (private per-user content, view-once access pattern, audience of one). If that ever changes, the documented upgrade is the same endpoint 302-redirecting to a short-lived presigned URL: auth stays in the backend, frontend unchanged, CDN/edge takes over delivery. ~20-line change inside the same handler.
- Scan pipeline: async, decoupled from upload request
    - Core invariant (decided): a receipt row is created upfront the moment work exists (upload, manual entry, recurring charge date) so no intermediate "waiting" state can lose work. All non-manual receipts require human review before counting toward stats/analytics — stats queries filter on the derived counts_in_stats predicate (reviewed_at present and at least as recent as any machine proposal; see Invariants), never on a raw status column.
    - POST /receipts saves image + creates receipt row (scan_state=uploaded), returns immediately
    - Background worker: in-process event-loop timer (`getLoop()->runEvery`) polling the scan_state column (no Redis/BullMQ at personal scale). Sets scan_state=scanning, calls scan service. Cap concurrent scans (~2-3).
    - Stuck-scan recovery (required, since in-flight scans die on process restart): receipts get scan_attempts + reclaim_count + scan_started_at; worker reclaims rows stuck in scan_state=scanning past a timeout. TWO separate budgets so deploy churn can't fail a good receipt (see Invariants): scan_attempts counts only real provider/parse errors (cap = 3 → scan_failed); reclaim_count counts crash/timeout reclaims (high backstop cap for genuine runaway hangs). A reclaim re-queues (scan_state=uploaded) WITHOUT spending a scan_attempt — "we never got an answer" is not evidence the scan is bad, and it must not pollute the <5% hard-failure quality metric.
    - Atomic job claim: worker claims jobs via `UPDATE ... WHERE id IN (SELECT ... WHERE scan_state='uploaded' FOR UPDATE SKIP LOCKED) RETURNING`, so the process stays stateless (DB is the queue's source of truth) and a second instance could never double-claim. Statelessness invariant: all in-process state (in-flight coroutines, timers, counters) is disposable and reconstructible from Postgres + MinIO.
    - Scan service (decided): multimodal LLM extraction, launch provider = Claude Haiku 4.5 (`claude-haiku-4-5`) via the Claude API with structured outputs (JSON-schema-constrained response) — ~0.5c/scan, guaranteed-parseable JSON.
    - Document-type classification (decided, M1 income): the scan is kind-aware — it first classifies the document (purchase receipt | return docket → refund | payslip/paycheck → income) and sets kind + direction accordingly, then extracts the fields appropriate to that type. Purchase/refund → merchant, date, total, currency, items, categories/tags. Payslip → employer (store_name_raw/merchant), pay date, NET pay as the income `total_cents` (magnitude, direction=inflow), income category (e.g. "salary") as ONE item (see Review, income items); gross/tax/super lines may be captured as best-effort informational items (informational=true) but NEVER feed stats/reconciliation (super boundary). Currency (decided 1b) is extracted alongside doc-type from whatever signal the document gives (symbol/text); defaults AUD only when undeterminable. The output JSON schema carries a `doc_type`/`kind` discriminator; category enums are context-appropriate (expense categories for receipts, income categories for payslips — both drawn from the user's own taxonomy via the is_income flag). One adapter, one schema with a discriminated shape — keeps the ScanProvider boundary unchanged.
    - Multi-image extraction (decided 1a): `ScanProvider.scanReceipt` takes a LIST of image bytes (not a single image) — all of a receipt's current images go into ONE multimodal call, so the model reconciles overlap/duplication/conflicting info across images itself (e.g. a correction email superseding a figure on the original photo) into one extraction result. A verify-rescan on attach/merge always resends the FULL current image set, not just newly added images, so context stays complete; this is why a per-receipt image cap exists (cost scales with image count on every rescan).
    - Payslip input note: paychecks are often digital PDFs; the M1 image pipeline (JPEG/PNG/WebP, no PDF rasterizer) expects an IMAGE, so a digital payslip is captured by SCREENSHOT (works today). Native PDF ingestion is out of M1 scope (would add a rasterizer dep — see Open Eng Decisions).
    - HARD REQUIREMENT — provider swappability: the scanner controller must make it trivially easy to swap any model from any LLM provider. Design: abstract `ScanProvider` interface (`scanReceipt(imageBytes/imageKey) -> ScanResult`), one adapter class per provider (Anthropic first; OpenAI/local/etc. later). Each adapter owns its own request shape, prompt, schema enforcement, and response parsing; the rest of the app only ever sees the normalized ScanResult struct. Provider + model + endpoint + API key come from config, not code, so a model swap within a provider is a config change and a new provider is one new adapter class.
    - On success: scan_state=idle + proposed_at stamped, structured fields + items written → the row derives as needs_review
    - On failure: scan_state=scan_failed, user can retry or enter manually
    - Frontend polls for status updates (simplest option at this scale; SSE/websocket possible later)
- Search (decided 1c): `SearchProvider` interface — `search(user_id, query, filters) -> ranked receipt ids`. M1 impl: Postgres ILIKE over merchant/store_name_raw/note (+ item names via join), scoped by user_id, composable with the existing filter set. Swappable later for a trigram/full-text index, Elasticsearch, or an LLM-based query interpreter without touching the frontend contract (`GET /search?q=`) — same swap-invisibility pattern as ScanProvider.
- Notifications (decided 1d): `Notifier` interface — `notify(user_id, event, payload)`. M1 impl: per-user Discord webhook URL (config-gated, no-op if unset). Triggers: weekly digest when the pending-review queue is non-empty (a scheduled timer job, same shape as the recurring-generation tick); terminal scan_failed after exhausted retries. Deliberately decoupled from the email-infra Open Eng Decision (verification/reset), which stays a separate concern.
- Recurring transactions (decided): when a recurring charge's expected date arrives, the worker immediately creates a receipt row (scan_state=idle, source=recurring, recurring_id FK, inheriting the definition's kind + direction, proposed_at stamped + reviewed_at NULL so it derives as needs_review). Works identically for outflows (charges, transfers) and inflows (recurring income like salary/interest). The row itself is the confirmation-queue entry: confirm = mark reviewed, cancelled/paused = delete. No separate recurring_charges table. Dedupe should offer to merge an uploaded receipt image into a matching pending recurring receipt rather than flag a duplicate.
- Recurring interval semantics (decided): month/year units use calendar arithmetic, not fixed day counts — monthly = (1, month), quarterly = (3, month), yearly = (1, year). Occurrence k is always computed from the anchor (anchor + k×interval), never from the previous occurrence, so clamping can't drift. Month-end clamping: if the anchor's day-of-month doesn't exist in a target month, clamp to that month's last day (Jan 31 → Feb 28/29 → Mar 31; Feb 29 anchor → Feb 28 in non-leap years) — matches Stripe/RFC 5545 behavior. All dates in Australia/Sydney. Real-world billing wobble (±days) is handled at review/dedupe-merge, not by the scheduler. Occurrence bookkeeping (decided): the definition stores occurrences_generated; occurrence k = that counter, so next_expected_date = anchor + (occurrences_generated+1)×interval (clamped) — the ordinal is tracked EXPLICITLY, not re-derived from the clamped date (which isn't cleanly invertible once month-end clamping applies). Generation is idempotent via a unique (recurring_id, occurrence_ordinal) on the generated receipts, so a double timer tick or a crash between insert and counter-advance can't double-create. Catch-up after downtime (decided): if several occurrences elapsed while the process was down, generate ONLY the latest missed occurrence (one receipt row) but ADVANCE occurrences_generated by the full elapsed delta to the latest elapsed ordinal — bills don't want N identical stale pending rows, yet the ordinal must still reflect reality so finite plans deactivate correctly. Skipped ordinals simply never get a row (the unique (recurring_id, occurrence_ordinal) permits gaps); a finite plan that slept through installments 2-3 resumes at 4 with occurrences_generated=4, so it still ends after the right number of cycles rather than running 2 cycles long. Single source of truth for "how far along" is occurrences_generated — see the finite-condition note in the schema (occurrences_total, not a separately-decrementing counter, to avoid two counters drifting).
- Auth (decided): session cookie — random token in a sessions table (only token_hash stored, never the raw token), httpOnly + Secure + SameSite=Lax, SPA served same-origin as API. Password hashing via libsodium argon2 (crypto_pwhash). JWT rejected: extra crypto machinery, awkward revocation, no benefit at this scale. First-party cookies are not affected by browser third-party-cookie blocking. Genuine multi-tenant (users table; ALL per-user rows scoped by user_id; ownership check on every route) — every signup is an equal peer, no owner/admin role, no first-user special case. Only-user-today is incidental.
    - Open self-service registration (decided — replaces the earlier first-user-only + REGISTRATION_TOKEN bootstrap, which is DROPPED): anyone can sign up like any SaaS. No privileged account means there is no "land-grab" to defend — registering first just creates your own empty isolated tenant. The concern shifts from privilege-theft to ordinary open-signup abuse, guarded the standard SaaS way (below).
    - Per-user seeding at registration (decided): creating a user also inserts THAT user's default category taxonomy + a "cash" payment method (stored_value=false). Seeds are per-tenant rows written in the registration transaction, NOT global rows in the migration — each tenant owns and can edit its own taxonomy independently.
    - Email verification + password reset (decided REQUIRED for public open signup; needs outbound email — SMTP or a transactional-email provider, new infra): verification gates spam AND cost abuse (every account can spend LLM scan money, so an unverified-signup flood is a direct bill); password reset is table-stakes for real multi-user. Both share the same email capability. Sending provider + whether these gate the M1 public launch = Open Eng Decision.
    - Sliding 30-day expiry, write-throttled (decided): a naive "touch expires_at on every authenticated request" write-amplifies every GET into a read+write. Instead only bump expires_at when it is more than SESSION_TOUCH_INTERVAL (default 1 day) stale — the session still slides, but the vast majority of requests stay read-only. Matters directly now that the tenancy model is real multi-user.
- Frontend (decided): vanilla JS + Vite + GSAP. Pure REST/JSON client, no server-side coupling to backend. No framework reactivity, so DOM updates for the status-polling UI are hand-rolled — keep a small render helper per view; a later framework rewrite stays possible since the API contract is the only coupling.
- Deployment (decided): public VPS. Consequences: auth is load-bearing, not defense-in-depth — Drogon behind a reverse proxy (Caddy recommended: automatic Let's Encrypt TLS), rate-limit the login endpoint, argon2 password hashing (already decided), enforce upload size limits at the proxy AND app layer, Docker Compose (app + Postgres + MinIO + Caddy) with vcpkg multi-stage build; MinIO not exposed through Caddy.
- API conventions (defaults, veto anytime): /api/v1 prefix; snake_case JSON; ISO-8601 UTC timestamps; error envelope {error: {code, message}}; offset pagination. All date bucketing (months, "today", FY) in Australia/Sydney, not UTC.
- Ownership authorization (decided): every resource route — reads, writes, and especially DELETE/merge-from — checks the row belongs to the session user; non-owned or missing ids return 404 (not 403, no existence leak). Load-bearing tenant isolation on a public multi-user host (not just future-proofing) and costs nothing (every query already carries the user_id predicate).
- Worker defaults: poll 5s; max 3 scan attempts (provider/parse errors only); reclaim scan_state=scanning after 10 min; 2 concurrent scans.
- Config/env knobs (decided, all defaulted so a fresh clone runs): SESSION_TOUCH_INTERVAL (sliding-expiry write throttle, default 1 day); match_total_abs_cents (default 200) + match_total_pct (default 0.05) for the imageless-candidate dedupe tolerance band; SMTP/email-provider settings (for verification + password reset — new infra, see Auth); the existing S3/provider/worker settings already come from config. Secrets (DB/MinIO creds, Anthropic key, email-provider key) live in .env / the deploy secret store, never in the repo (success-criteria security floor). (The earlier REGISTRATION_TOKEN knob is removed — open signup has no bootstrap token.)
- Upload constraints: 15MB max (enforced at Caddy AND app); server accepts JPEG/PNG/WebP ONLY and rejects HEIC at the app layer — the pinned libvips build (jpeg,png,webp,exif; NO HEIF decoder) cannot decode HEIC, so client-side HEIC→JPEG conversion is MANDATORY, not an optimization; client also downscales before upload; server normalizes regardless (see Object storage). (If server-side HEIC is ever needed — e.g. post-M1 email-in ingestion from clients we don't control — it's a vcpkg feature add (libvips[heif]) that must be re-verified on arm64-osx, which the current build deliberately avoids.)
- Client-side conversion mechanism (decided — "mandatory" needs a named, load-bearing implementation, not a hope): the primary phone-capture path is iOS Safari, which CAN decode a HEIC file into an `<img>` / `createImageBitmap`, so the default downscale-and-reencode path (draw to a `<canvas>`, `canvas.toBlob('image/jpeg' | 'image/webp')`) handles HEIC there for free — the same canvas step that does the pre-upload downscale also drops HEIC. Fallback for browsers that CANNOT natively decode HEIC (notably desktop Chrome/Firefox): a lazily-loaded `libheif` WASM decoder (~1-2MB, imported only when a `.heic`/`.heif` is detected and the canvas decode fails), converted to a File before it enters the shared downscale pipeline. Detection is by decode-failure, not filename, so mislabeled files still work. Rationale for lazy-load: the WASM is dead weight on the 99% JPEG/WebP path and on iOS where it's never needed. If canvas decode fails AND the WASM fallback fails, the client refuses the file with a clear message rather than uploading a HEIC the server will reject.
- Category seed list — applied PER USER at registration (not a global migration seed; each tenant gets its own editable copy). Expense categories (is_income=false): groceries, dining/takeaway, transport, fuel, household, utilities, subscriptions, insurance, health, clothing, entertainment, gifts, fees, bonds/deposits, rewards, work-expenses, junk food, other. Income categories (is_income=true): salary, interest, dividends/distributions, other-income.
- Payment-method seed — also PER USER at registration: "cash" (stored_value=false) only — required so quick-add's payment=cash default resolves for every new tenant; all other methods are user-created in-app. (Both seed sets are template constants in code, written as that user's rows inside the registration transaction.)
- Backups: nightly pg_dump + rclone of dump and MinIO data to offsite target (target chosen at VPS setup; B2 default); restore drill per success criteria.
- Dev environment: macOS (clang) for development, Linux (Docker) for deploy; Compose file doubles as dev env (Postgres + MinIO); Vite dev server proxies /api to Drogon; Linux CI catches platform drift.
- Dual-architecture (decided, hard requirement): everything must work on arm64 (macOS local dev) AND x86_64 (Linux VPS). Consequences: all deps must be available on both (Postgres/MinIO/Caddy images are multi-arch; vcpkg deps must build on arm64-osx and x64-linux — libvips[jpeg,png,webp,exif] 8.18.2 VERIFIED building + producing WebP on arm64-osx 2026-07-11; host prerequisite: `brew install autoconf autoconf-archive automake libtool`); local dev runs the app natively on macOS against arm64 containers (no emulation); the x86_64 deploy image is built ONLY in CI (Step 3) — never on the Mac, where QEMU cross-building a C++ image would take hours; no arch-specific code (intrinsics, asm) without a portable fallback.

- Schema (draft):
    - Enum representation (decided): every bracketed enum below (kind, direction, scan_state, interval_unit, source) is a TEXT column + CHECK constraint, NOT a native Postgres ENUM type. Rationale: `ALTER TYPE ... ADD VALUE` (e.g. adding `income` to kind in M1, or any future kind) cannot run inside a transaction on older PG and is irreversible — hostile to dbmate's plain up/down SQL. A CHECK constraint is dropped/recreated in an ordinary reversible migration. Same validation guarantee, clean evolution. (kind provably grows over time; the rest use the same representation for consistency.)
    - users(id, email UNIQUE (case-insensitive — citext or a lower(email) unique index), password_hash, email_verified_at nullable, created_at) — one tenant per row, all equal; verification/reset tokens stored hashed with a short expiry (a small auth_tokens(user_id, token_hash, purpose[verify|reset], expires_at) table, or reuse the sessions pattern — finalize with the email decision)
    - sessions(id, user_id, token_hash, expires_at, created_at)
    - categories(id, user_id, name, is_income BOOL DEFAULT false) — one user-editable taxonomy; is_income splits it into expense categories and income categories. The category picker filters by context (kind=income → income categories; else expense); the scanner embeds the context-appropriate subset as its enum. Categorization is ITEM-LEVEL ONLY (decided 2a — see Review): ≤1 category per item, NONE at receipt level (receipts.category_id is REMOVED). Referencing FKs ON DELETE SET NULL (delete → referencing items become uncategorized, live; rename keeps the stable id). Income-category seeds: salary, interest, dividends/distributions, other-income (per-user at registration, like expense categories).
    - tags(id, user_id, name) — second user-editable taxonomy, ITEM-LEVEL ONLY, 0..N per item; embedded as enum in the scanner's per-item output schema (LLM-proposed, best-effort)
    - item_tags(item_id, tag_id) — many-to-many join; PK (item_id, tag_id); both FKs ON DELETE CASCADE (delete a tag or an item → associations vanish, live)
    - payment_methods(id, user_id, name, stored_value BOOL) — user-managed list ("Amex", "Visa …1234", "cash", "Opal", "gift card"); stored_value=true methods are excluded from spend stats at payment time
    - receipts(id, user_id, store_name_raw (also holds employer name on a payslip), merchant, purchase_date (pay date on income), total_cents BIGINT ≥ 0 (NON-NEGATIVE magnitude — see Money), direction[inflow|outflow] (cashflow/reconciliation side; CHECK-consistent with kind for fixed kinds — purchase→outflow, refund/reimbursement/income→inflow — free for transfer), currency CHAR(3) DEFAULT 'AUD', fx_rate_to_aud NUMERIC nullable (decided 4a — user-entered, e.g. the exchange-booth/ATM rate; a point-in-time decision, not a market feed), aud_equivalent_cents BIGINT nullable (computed from fx_rate_to_aud at entry/edit time, NOT live-recomputed; feeds only the opt-in Combined view, see Insights), kind[purchase|refund|reimbursement|income|transfer] (TEXT+CHECK, extensible), scan_state[idle|uploaded|scanning|scan_failed], scan_attempts, reclaim_count, scan_started_at, proposed_at, reviewed_at, payment_method_id FK nullable (ON DELETE SET NULL), tax_deductible (CHECK: only true when kind='purchase' — decided 2b, backed by app-layer validation too; a refund/income/transfer marked deductible is meaningless), note, source[scanned|manual|recurring], recurring_id FK nullable (ON DELETE SET NULL), occurrence_ordinal nullable (set only on recurring-generated rows; unique (recurring_id, occurrence_ordinal) → idempotent generation), offsets_receipt_id FK nullable (refund/reimbursement → original expense; ON DELETE SET NULL), raw_ocr_json, created_at, updated_at)
      - `category_id` is REMOVED from receipts (decided 2a — categorization is item-level only, see Review); `image_key`/`image_sha256` are REMOVED from receipts (decided 1a — moved to receipt_images, a receipt now owns a SET of images, see below)
      - the table is really a general TRANSACTIONS ledger (receipts, cash, income, transfers) — "receipts" is a legacy name; an income/interest/salary row is a normal zero-image row or a scanned payslip
      - stats/charts group by (or filter to) currency — never sum across currencies natively; the opt-in Combined view (4a) is the one explicit exception, clearly separate
      - index (user_id, currency, total_cents, purchase_date) — serves the match-panel candidate query across full history. Currency leads (candidates match WITHIN the same currency — total_cents is currency-relative, 50 USD and 50 AUD both store 5000 and must not false-match), then total_cents supports a bounded range scan (candidate.total ± tolerance band, the single matching rule for all candidate flavors — see Dedupe), and purchase_date narrows the ± days window. (The exact-image-dup case is caught upstream by the receipt_images.image_sha256 hash at upload time, not by this query.)
      - store_name_raw = what the scan extracted ("WOOLWORTHS 1234 CHATSWOOD"); merchant = normalized name for dedupe/charts, editable at review
      - NO stored status enum for review: review/stats state is DERIVED from (proposed_at, reviewed_at) — needs_review ⇔ proposed_at present AND (reviewed_at NULL OR proposed_at > reviewed_at); counts_in_stats ⇔ reviewed_at present AND (proposed_at NULL OR reviewed_at ≥ proposed_at). scan_state is ONLY the scan-pipeline lane (idle = at rest incl. manual/recurring/scan-complete; uploaded = queued; scanning = in flight; scan_failed = terminal + retryable). proposed_at = last machine proposal (scan completion OR recurring auto-creation); reviewed_at = last human confirmation. See Invariants.
      - Derived predicates live in ONE place, not inlined per query (decided) — but LAYERED, because "confirmed & current" and "counts as spend" are different memberships and some views need the former without the latter:
        - `v_receipt_state` — the base view: every receipts column plus two derived booleans computed from timestamps ALONE — `needs_review` and `is_confirmed` (= reviewed_at IS NOT NULL AND (proposed_at IS NULL OR reviewed_at ≥ proposed_at)). This timestamp logic (the ≥/> boundary between the two) is the highest-risk correctness surface in the app; single-sourcing it here and pointing the Invariants tests at it is the whole point.
        - `v_countable_spend` — spend membership at the RECEIPT level (for stats that don't need category — monthly trend, tax-FY total, reconciliation inputs), built ON v_receipt_state: is_confirmed AND kind IN ('purchase','refund','reimbursement') AND NOT (kind = 'purchase' AND the payment method's stored_value flag) via the payment_methods join. NOTE (decided 2026-07-18, income pivot): the predicate is an explicit spend-kind ALLOWLIST, NOT "kind ≠ transfer" — with income now a kind, "≠ transfer" would wrongly pull salary into spend. The view also exposes a `signed_spend_cents` = total_cents × (kind='purchase' ? +1 : −1), so receipt-level spend stats just SUM that column (per-kind sign single-sourced in the view, not re-derived per query). This is the Invariants `counts_in_stats`.
        - `v_income` — income membership at the RECEIPT level, built ON v_receipt_state: is_confirmed AND kind = 'income'. Exposes total_cents as a positive magnitude (all inflow).
        - `v_countable_spend_items` / `v_income_items` (decided 2a — item-level counterparts, added for the item-only-categorization pivot): items JOINed to v_countable_spend / v_income respectively, filtered to `items.informational = false`, exposing item.category_id and a signed item amount (same per-kind sign rule as the receipt-level view). ALL category-based insights (category breakdown, income-by-category, item-category filtered trend) select through these, not through the receipt-level views or any receipt-level category column (there is none — see above). This is why category breakdown and item-category trend collapsed into one mechanism instead of two that could disagree.
        - The RECONCILIATION stats deliberately use neither spend/income view wholesale — they need direction-based membership across kinds: the cash view needs kind=transfer (ATM withdrawals) vs cash purchases; the payment-method crosscheck reconciles what actually hit the bank (both sides now that income is in M1) and so joins across kinds by `direction` (inflow=credit, outflow=debit), treating stored-value-paid purchases per the bank-debit reality. Both select through v_receipt_state (is_confirmed) with their own kind/direction/payment filters. Collapsing exclusions into the base view would have broken these — the reason the design is layered.
        - Why views not a GENERATED column: the stored-value exclusion needs the payment_methods join, and generated columns can't reference other tables. The timestamp booleans alone (no join) could be generated columns, but keeping them in v_receipt_state alongside is_confirmed is simpler.
      - Stored-value exclusion is a LIVE join to payment_methods.stored_value (decided consequence, symmetric with the delete case in Invariants): because v_countable_spend (and v_countable_spend_items, built on it) joins the flag live, TOGGLING a method's stored_value flag retroactively flips ALL its past purchases in/out of spend stats on the next query — same root cause as deleting the method un-excluding its purchases. Intended (matches the live-join philosophy used for categories); flagged here so it isn't a surprise. If per-receipt exclusion ever needs to be frozen at record time, snapshot the exclusion bit onto the receipt (also noted in Invariants).
    - receipt_images(id, receipt_id FK ON DELETE CASCADE, user_id (denormalized for the dup-check index — decided 1a), image_key, image_sha256 nullable (normalized image; indexed, non-unique — force=true permits genuine re-uploads), created_at) — a receipt owns 0..N images (config cap, default 8); replaces the old single image_key/image_sha256 columns on receipts (see Capture, multi-image receipts)
      - index (user_id, image_sha256) — the exact-duplicate check scans across every image the user owns, not per-receipt; scoped by user so it can't leak another account's receipt existence
    - items(id, receipt_id, name, quantity, unit_price_cents, amount_cents, category_id FK nullable (ON DELETE SET NULL), informational BOOL DEFAULT false (decided 2a — payslip gross/tax/super breakdown lines etc.; excluded from every amount-sum, category-breakdown aggregation, and the sum-mismatch warning)) — item↔tags is many-to-many via item_tags (0..N). Items are now load-bearing for categorization (decided 2a — see Review): manual/quick-add entry auto-creates one implicit item per receipt so category breakdown stays item-sourced everywhere; item REVIEW stays optional, item EXISTENCE does not.
    - Price-component extensibility (decided): no GST/tax amount stored in M1, but amounts must be splittable later into components (base + gst + service charge + card surcharge + holiday surcharge, …) as added columns on receipts/items. What this requires NOW: total_cents/amount_cents stay the single authoritative charged amounts (future component columns reconcile to them); NO DB constraint tying receipt total to sum(items) — the sum-mismatch check is a review-UI warning only. Docket-line surcharges are representable today as items categorized under fees.
    - recurring_transactions(id, user_id, name, merchant, kind[purchase|transfer|income], direction (canonical for the kind; income→inflow), expected_amount_cents (magnitude ≥ 0), currency, interval_n, interval_unit[day|week|month|year], anchor_date, occurrences_generated (occurrence ordinal k, the SINGLE mutable progress counter; next date = anchor + (occurrences_generated+1)×interval, clamped — see interval semantics), next_expected_date (materialized from the ordinal for the worker's due-date query), end_date nullable, occurrences_total nullable (finite target: deactivate when occurrences_generated ≥ occurrences_total — a FIXED target, not a decrementing counter, so it can't drift against occurrences_generated during catch-up), purchase_receipt_id FK nullable (installment plans → what was bought; ON DELETE SET NULL), default_payment_method_id, default_category_id (seeds the implicit item's category on each generated row, same UI-sugar mechanism as manual entry — decided 2a, not a receipt-level field), default_tax_deductible, active)
      - auto-deactivates when end_date passes OR occurrences_generated ≥ occurrences_total (both derived from stable inputs — no separate decrementing counter to keep in sync). "Remaining" for display = occurrences_total − occurrences_generated.
      - generated pending receipts carry the occurrence ordinal; a unique (recurring_id, occurrence_ordinal) makes generation idempotent (crash/double-tick safe); catch-up generates only the latest missed occurrence but advances occurrences_generated by the full elapsed delta so finite plans still end on count (see interval semantics)
    - (recurring_charges table removed — the auto-created pending receipt is the confirmation-queue entry)

# Invariants (load-bearing — each gets a test)

Cross-cutting rules multiple features depend on. They're easy to violate in code, so they're stated once here and each is covered by a test.

- **Zero-loss:** a receipt row exists the instant work exists (upload, manual entry, recurring due-date), and each image is persisted (a receipt_images row) the instant it's accepted — whether it's a receipt's first image or its fifth (decided 1a, multi-image receipts). No in-memory-only state can lose work. All in-process state (coroutines, timers, counters) is disposable and reconstructible from Postgres + MinIO.
- **Item-level categorization (decided 2a):** `receipts.category_id` does not exist — all category-based membership/aggregation (category breakdown, income-by-category) goes through items (`v_countable_spend_items` / `v_income_items`), filtered to `informational=false`. A receipt with zero items is honestly "uncategorized," never silently mis-attributed via a receipt-level field. Manual/quick-add entry's single category field is UI sugar over one implicit item — this must never regress into a parallel receipt-level categorization path.
- **Two-axis state (there is NO `status` column):** a receipt's lifecycle is two orthogonal axes.
    - scan_state[idle|uploaded|scanning|scan_failed] — the scan-pipeline lane ONLY. idle = at rest (manual, recurring, or scan-complete); uploaded = queued for the worker; scanning = in flight; scan_failed = terminal-but-retryable.
    - review/stats state — DERIVED from two timestamps, never stored:
        - proposed_at = last time a machine proposed field values (scan completion OR recurring auto-creation).
        - reviewed_at = last time a human confirmed the row.
        - needs_review ⇔ proposed_at IS NOT NULL AND (reviewed_at IS NULL OR proposed_at > reviewed_at)
        - counts_in_stats ⇔ reviewed_at IS NOT NULL AND (proposed_at IS NULL OR reviewed_at ≥ proposed_at), further filtered by the stats rules (kind ≠ transfer; not a stored-value-paid purchase).
    - Single-source predicate (layered): the timestamp membership (needs_review, is_confirmed) is defined ONCE in the SQL view `v_receipt_state` (migration 001), never re-inlined. Spend membership (`counts_in_stats` = is_confirmed AND kind IN (purchase,refund,reimbursement) AND not a stored-value-paid purchase — an explicit spend-kind allowlist, NOT "≠transfer", so income is not swept in) is `v_countable_spend` (which also carries the signed_spend_cents column); income membership is `v_income` (is_confirmed AND kind=income); reconciliation stats reuse the base v_receipt_state because they NEED the transfer / income / stored-value rows and slice by `direction`. The Invariants tests target the views; every stats/queue endpoint selects through the appropriate layer (see schema).
    - Designed-in consequence (this REPLACES the old "stats blip"): proposed_at is stamped only when a scan COMPLETES, so a reviewed receipt being re-scanned (attach/merge) stays in stats through the whole in-flight window and even across a crash + reclaim; it leaves stats only at the instant a completed scan finds a mismatch.
- **Trust-gated scan mode:** reviewed_at IS NULL → extraction (scan writes fields); reviewed_at IS NOT NULL → verify (fill-empty-only + compare, never overwrite). Provenance (`source`) does NOT gate this — a manually-filled scan-failed row is verify-mode on retry.
- **Scan-attempt vs reclaim budgets:** scan_attempts counts only real provider/parse errors (cap 3 → scan_failed); reclaim_count counts timeout/crash reclaims (high backstop cap). A reclaim re-queues WITHOUT spending a scan_attempt, so deploy churn can't fail a good receipt or pollute the <5% hard-failure metric.
- **Recurring generation is idempotent:** unique (recurring_id, occurrence_ordinal); ordinal tracked via occurrences_generated (the single mutable progress counter); catch-up generates only the latest missed occurrence but advances occurrences_generated by the full elapsed delta, so a finite plan (occurrences_total target, not a decrementing counter) still ends after exactly N cycles even after downtime.
- **Equal-tenant registration:** registration is open self-service; every account is an equal isolated peer (no owner/admin role, no first-user privilege). Creating a user seeds THAT user's default categories + "cash" payment method in the same transaction. Email is unique per user (case-insensitive); no global state distinguishes one account from another.
- **Referential cleanup:** inbound receipt FKs (offsets_receipt_id, recurring_id, purchase_receipt_id) and the receipt-level reference-data FK (payment_method_id) are ON DELETE SET NULL; items.category_id (the only category FK — receipts no longer have one, decided 2a) is ON DELETE SET NULL; item_tags and receipt_images are ON DELETE CASCADE; merge repoints inbound receipt FKs source→target and moves all of the source's receipt_images before deleting the source. Accepted consequence: deleting a stored-value payment method un-excludes its past purchases from spend (they re-enter stats under "no payment method") — payment methods aren't meant to be deleted; if this ever bites, snapshot just the exclusion bit onto the receipt.
- **Tenant isolation (load-bearing, now that multi-user is real not hypothetical):** every resource query carries the user_id predicate; non-owned/missing id → 404 (no existence leak). No endpoint can read, join, or mutate across tenants. The image_sha256 dup check is scoped (user_id, image_sha256); the scanner's category/tag enums are built from the requesting user's own taxonomy. A cross-tenant read is a security bug, not a nuisance — each gets a test.
- **Money:** integer cents end-to-end, stored as a NON-NEGATIVE magnitude (direction is the separate `direction` field, never the amount's sign); per-kind stat signs live in the views (signed_spend_cents), not in storage; dedupe/match compares magnitude within a single currency; stats group by currency, never sum across. Spend membership is a spend-kind ALLOWLIST (purchase/refund/reimbursement), not "≠transfer" — income must never leak into spend.

# Success Criteria

Priority (decided): **daily-use tool first**. Success = still using it in 6 months. When instructive-but-slow conflicts with shipping, ship — C++ learning is pursued opportunistically within that constraint, never as a reason to stall a feature.

## Product — the app is genuinely used
- Capture bar (decided): EVERY transaction — receipts, cash, cards, subscriptions, AND income (paychecks, interest, distributions). The app is the complete money record (both sides), not just spending; bank reconciliation should fully balance on debits AND credits, not approximately.
- Habit: after M1 ships, transactions are captured within 3 days of purchase, sustained for 3 consecutive months without reverting to spreadsheets/nothing.
- Friction ceilings (these make the every-transaction bar survivable): recording a cash transaction <15s (implies a quick-add form with smart defaults, not a full page of fields); typical scanned receipt reviewed in <30s; pending-review queue hits zero at least weekly.
- Zero-loss invariant holds in practice: no receipt ever disappears into a waiting state; every upload is accounted for as reviewed, pending, or failed-with-image.
- Trust: monthly payment-method totals reconcile against bank statements fully on BOTH sides — debits (spend/transfers out) AND credits (income, refunds, reimbursements, transfers in), matched by direction (income is in M1 scope now); discrepancies explainable in minutes, not hours. (Off-bank flows — employer super SG, salary-sacrifice, gross/PAYG — are intentionally excluded: only bank-touching amounts are tracked.)
- Tax time test: at FY end, producing the deductible receipt list + CSV export takes <5 minutes.

## Scanner quality (measured against the golden set)
- Golden set: 20-30 real receipt photos (varied: faded thermal, crumpled, long dockets, glare) with hand-verified expected values, kept as fixtures, PLUS a handful of payslip/paycheck images (income scanning is in M1) — different layout, so a few fixtures guard the doc-type classifier + net-pay extraction — PLUS a few multi-image grouped fixtures (decided 1a; e.g. two overlapping shots of one long docket, or a receipt + a correction screenshot) to guard the multi-image reconciliation path specifically, since that's a new failure surface (the model merging conflicting/overlapping inputs badly is a different bug class than misreading a single image). Re-run on every prompt/model/provider change — the regression harness that makes provider swapping safe, not just easy.
- Field accuracy targets (proposed): receipts — total ≥98%, purchase date ≥95%, merchant ≥90%, item category ≥80% (was "receipt category" — categorization moved item-level, decided 2a; measured on the item(s) actually created for a receipt); payslips — doc-type classified correctly ≥98%, NET pay amount ≥98%, pay date ≥95%, employer ≥90%. Items / gross-tax-super breakdown best-effort, no gate.
- Hard scan failures (scan_failed after retries) <5% of uploads.

## Engineering & ops
- Restart-safe: killing the process at any moment loses no data; stuck scans self-recover via the reclaim rule (verified by test).
- Deploy is one command (docker compose up on the VPS); a fresh-machine rebuild from repo works, proving the vcpkg/CMake setup is reproducible.
- Backups: Postgres + images backed up automatically; a restore drill has actually been performed once (an untested backup doesn't count).
- Security floor on the public VPS: TLS via Caddy, rate-limited login AND registration (per-IP AND per-account, decided 3b), argon2 hashing, open signup guarded by email verification (spam + LLM-cost-abuse gate), strict per-tenant isolation (cross-tenant read = failing test), password reset invalidates all sessions (decided 2c), no secrets in repo. Further hardening tracked as a backlog, not a launch gate — see Security Improvements.
- Running cost: (proposed) <$15/month all-in (VPS + LLM; LLM share expected <$1).

## C++ learning outcomes (decided: all four, subordinate to shipping)
- Async & coroutines: can add a new endpoint end-to-end (route → coroutine handler → async SQL → JSON response) without copying from references; can explain why blocking the event loop is wrong and demonstrate the failure mode.
- Ownership & RAII: no raw owning pointers in the codebase; can justify each lifetime/ownership decision (value vs unique_ptr vs shared_ptr) rather than defaulting to shared_ptr everywhere.
- Build & tooling: owns the CMake + vcpkg setup rather than cargo-culting it; dev builds run with warnings-as-errors and ASan/UBSan; fresh-machine rebuild from repo works.
- Testing discipline: unit tests (Catch2 or GoogleTest) + integration tests against Postgres are a habit, not an afterthought; FakeScanProvider exercises the review pipeline without LLM calls; tests run before every deploy.

## M1 definition of done
- All M1 user stories implemented and exercised with real data: one full month of real receipts/transactions processed through the system.
- Golden-set accuracy targets met; restore drill passed; a full FY-style CSV export produced.
